# 평가 실행 계약 — v5.0

전체 파이프라인과 자소서 평가·진단 요청에서는 이 절차를 끝까지 실행한다. 단일 문항 작성·부분 윤문 요청에는 전체 채점을 자동 추가하지 않는다. 점수는 검토자의 판단을 요약한 내부 참고 지수이며 합격률로 보정되지 않았다.

## 입력

`draft.txt`는 `===1===` 같은 문항 ID 구분자로 시작한다. 헤더 밖의 메모와 중복·빈 문항을 허용하지 않으며 spec과 문항 ID가 일치해야 한다. 현재 CLI는 draft.json을 직접 받지 않는다.

```text
===1===
첫 번째 답변 본문
===2===
두 번째 답변 본문
```

`spec.json`은 `questions` 객체에 각 문항의 다음 정보를 담는다.

- `prompt`: 실제 문항 원문과 요구 조건. 원문을 확보하지 못하면 null/생략으로 남기며 E/F는 적용된 경우 반드시 DEFERRED로 유보한다. 축약 제목을 완전한 원문으로 취급하지 않는다.
- `min`, `max`, `basis`: 확인된 분량 조건. 최소가 없으면 0, 최대가 없으면 생략한다. `basis`는 실제 린트가 지원하는 `with_spaces`, `without_spaces`를 쓰고, 바이트 계수는 `length_metric_type`의 지원 값을 확인한다. 사용한 계수 방식과 줄바꿈 처리 기준을 보고한다.
- `applicable_axes`: 이번 문항과 본문의 주장에 적용할 축 목록. 평가 전에 정하고 결과에 맞춰 제외하지 않는다.
- `axis_applicability_reasons`: A/B/C/D/E/F/H/I 각 축의 적용 또는 제외 이유. 제외 축은 아래 평가 JSON에서 N/A로 처리한다.
- `required_items`: 탐색을 돕는 키워드. 부재 자체를 문항 미충족으로 단정하지 않는다.

적용 기준은 루브릭 JSON에 있다. A는 필요한 맥락과 개인 과제·행동, B는 판단의 근거, C는 역할·행동·결과, D는 요구된 직무 연결, E/F는 질문과 명시 요구, H는 구체성, I는 요구된 태도를 본다. G 규격과 J 근거 대조는 작성 점수에서 분리했다. 예를 들어 협업 질문에 회사 적용 요구가 없으면 D를 제외할 수 있다. 사회 이슈에 프로젝트 수행 결과가 필요하지 않으면 C를 제외할 수 있다. 필수 작성 요구를 임의로 제외하지 않는다. 분리된 규격·사실 확인도 보고서에 보존한다.

`context.json`은 선택한 회사·직무의 사실과 출처, 경험 본문·주장별 근거를 담는다. 자료 원문 대신 결론만 주지 않는다. 작성자 칭찬, 면책 요구, 목표 점수, 과거 합불은 넣지 않는다. 근거가 없는 회사 내부 과제는 알려진 사실처럼 넣지 않는다. 개인 경험 자료가 없어도 사용자 진술로 작성 평가를 진행한다. 선택적 근거 대조의 sources/claims 형식과 첫 사용자 경로는 [근거 대조 계약](fact-checking.md)을 읽는다.

구형 spec에 문항 원문이나 적용 축이 없으면 [구형 자료 이전](migration.md)을 따른다. 새 필드를 사용자가 직접 만들게 넘기지 않고 호스트가 실제 공고와 문항을 읽어 별도 사본을 준비한다.

`recruitment_track_type`에 따른 인턴/신입/경력 지침이 두 평가 패킷에 들어간다. 트랙 미확인·혼합이면 임의 경력 수준을 선택하지 않는다. 실제 공고의 요구와 본인 주장 범위가 기준이며 트랙별 자동 점수 보정은 없다.

[문항별 작성 흐름](question-flows.md)은 작성과 평가가 공유하는 내용 기준이다. 패킷의 원문 질문에서 해당 유형을 선택하고, 담당 축의 판단 이유에 본문의 어떤 설명 연결이 성립하거나 부족한지 남긴다. 작성 개요·컨설팅 예문·과거 합격 원고를 이번 원고의 증거로 대신하지 않는다.

## 패킷 생성

```sh
python3 scripts/run_pipeline.py /absolute/path/draft.txt /absolute/path/spec.json --context /absolute/path/context.json
```

입력 구조가 유효하면 규격 검사 결과와 함께 초안 파일 옆의 `scratch/runs/<run_id>/packets/`에 평가자별 패킷과 린트 결과, `session_token.json`을 만든다. 패킷 생성은 평가자 호출이나 채점 완료가 아니다. 현재 스크립트는 모델 API를 호출하지 않으며 원장/Notion에도 자동 기록하지 않는다.

토큰은 draft·spec·context·루브릭·공통 문항별 작성 흐름·린트 결과·평가 패킷·실행 코드의 해시, 실행 ID와 가중치를 묶는다. 다른 입력을 섞거나 파일이 바뀌면 새 패킷을 만든다. 해시는 입력 동일성을 검사하지만 작성자의 편향이나 실제 에이전트 격리를 증명하지 않는다.

## 독립 실행

작성 대화를 상속하지 않는 새 컨텍스트에서 HR와 TECH를 각각 실행한다. Codex 협업 도구를 쓰는 경우 `fork_turns="none"`을 사용한다. 최소 지시 예시는 ‘이 패킷 파일을 읽고 평가하여 지정 경로에 JSON으로 저장하라’다. 추가 칭찬·변론·예상 점수·실제 합불을 주지 않는다.

평가자별 호출 기록·모델·실행 시각·패킷 경로를 작업 기록에 남긴다. 실제 호출이나 격리를 확인할 수 없으면 ‘독립 평가 완료’라고 보고하지 않는다. 동일 모델의 공통 편향이 제거됐다고 주장하지 않는다.

패킷에 출력 JSON 틀이 들어 있다. 최상위에 `evaluator`, `run_id`, `draft_hash`, `packet_hash`, `questions`가 필요하다. 문항마다 담당 4개 축의 `scores`와 `axis_evidence`를 모두 기록한다. 적용 축은 정수 1~5 및 다음 근거를 낸다. 개인 경험 자료의 부족은 점수 사유가 아니다.

```json
{
  "status": "ASSESSED",
  "quotes": ["해당 문항 본문에 실제 존재하는 연속 인용"],
  "rationale": "이 문장이 평가 기준을 충족하거나 보완이 필요한 구체적인 이유",
  "severity": "none"
}
```

`severity`는 `none`(글의 추가 수정 없음), `revise`(글의 실제 수정 필요)다. 자료 확인은 fact_review로 분리한다. 적용하지 않는 축은 점수 `null`, `status: "NOT_APPLICABLE"`, `reason`을 낸다. 낮은 점수와 수정 필요 없음은 모순이므로 거부한다. 필수 문항·직무 입력이 없어 판단할 수 없는 축은 점수 null, status DEFERRED, missing_input(prompt/job_description/required_instruction), reason을 남긴다. 한 축이라도 유보된 문항과 종합 평균은 null이다. 경험 증빙 부재는 유보 사유가 아니다.

정확한 인용은 공백 정규화 외에는 원문과 일치해야 한다. 다른 문항의 인용, 의미만 비슷한 문장, 빈 인용은 거부한다. 내용 누락을 지적할 때도 관련 실제 문장을 인용하고 빠진 것을 설명한다. 긍정 평가도 근거를 설명한다. ‘결함을 못 찾음’은 자동 만점 사유가 아니다.

### 독립 TECH의 면접 검토

TECH는 각 문항에 `fact_review: {"findings": [...]}`와 `interview`도 제출한다. 근거 대조 연결표가 없으면 findings=[]이며 정상 입력이다. 자세한 대조 형식은 [근거 대조 계약](fact-checking.md)을 따른다. `questions` 배열의 각 항목은 `topic`(technical/organization), `question`, `intent`, `anchor_quote`, `answer_scope`, `facts_to_confirm` 배열을 가진다. 원고·경험 자료로 답할 수 있는 범위와 추가 확인할 사실을 구별한다. 질문이 필요 없으면 빈 배열과 구체적인 `omission_reason`을 낸다. 고정 개수를 채우지 않는다.

새 토큰의 `technical_followups_required: true`는 이 검토가 요청됐음을 표시한다. 누락한 TECH 응답이나 원고와 다른 면접 인용은 집계에서 거부한다. 인용 검증만으로 답변 내용의 진실성이 보장되지는 않으므로 호스트도 원문과 범위를 대조한다. 호스트 추가 질문은 별도 출처로 표시하고 독립 평가 결과에 끼워 넣지 않는다.

## 집계와 해석

```sh
python3 scripts/run_pipeline.py /absolute/path/draft.txt /absolute/path/spec.json --context /absolute/path/context.json --hr-eval /absolute/path/hr_eval.json --tech-eval /absolute/path/tech_eval.json --session-token /absolute/path/session_token.json --out /absolute/path/report.md --out-json /absolute/path/aggregate.json
```

입력 해시·실행 ID·문항·역할·적용 축·인용이 모두 유효해야 집계한다. 가중치는 평가 전에 정하며 기본 0.4/0.6은 이전 버전과 비교를 위한 내부 관례일 뿐 채용사의 실제 비중이 아니다. 평가 중 점수를 맞추기 위해 바꾸지 않는다. 적용 축의 수가 다르면 문항 간 지수도 직접적인 우열로 해석하지 않는다.

`grade.py`는 문항별 HR/TECH 지수·가중 지수, HR/TECH별 문항 평균, 종합 평균, 작성 보완 항목, 규격 상태, 선택적 사실 대조, 독립 면접 질문을 직접 출력한다. `--out-json`에는 같은 계산 결과와 원 실행·입력 해시를 저장한다. 적용 축이 없는 역할은 0점이 아니라 null/N/A이며 그 문항의 가중치 분모에서도 제외한다. 역할 평균은 해당 역할이 적용된 문항만 평균한다.

가중치 프리셋은 `--weight-profile BALANCED`(HR:TECH 4:6), `TECH_DRIVEN`(3:7), `HR_PUBLIC_DRIVEN`(6:4)다. 이름은 과거 사용 관례이며 실제 업종별 채용 비중을 뜻하지 않는다. 기본은 BALANCED와 같고 `--hr-weight`/`--tech-weight`로 직접 정할 수도 있다. 프리셋과 직접 지정을 동시에 하지 않는다. 생성·집계 양쪽에 같은 선택을 전달한다.

생성 후 24시간 이상 지난 평가를 재사용하면 정보 알림을 표시한다. 시간 경과로 만료시키지 않으며 입력·코드 해시가 바뀐 경우는 별도로 재평가가 필요하다. 조직 관계 가이드는 제공된 채용 법인·담당 서비스와 관계 근거를 출력하고, 근거가 없으면 미확인으로 남긴다.

- `NOT_EVALUABLE`: 입력 또는 평가가 누락·무효. 점수를 산출하지 않는다.
- `INPUT_INCOMPLETE`: 필수 문항·직무 입력 부족으로 작성 축을 유보함. 해당 문항·종합 점수는 null이다. 경험 증빙 부재는 해당하지 않는다.
- `REVISION_REQUIRED`: 구체적인 보완점이 남음.
- `REVIEW_COMPLETE`: 현재 패킷의 검토 절차가 완료됨. 합격권·사실 완벽 검증·제출 승인을 뜻하지 않는다.
- `HISTORICAL_UNVERIFIED`: 구형 기록을 `--historical-import`로 열람한 상태. 현재 점수를 만들지 않는다.

해시·인용 검증 실패는 만점 복원이 아니다. 입력을 고친 뒤 필요한 평가를 다시 한다. `--allow-stale`로 검증을 우회할 수 없다. 같은 입력의 유효한 과거 평가를 재사용할 때는 재사용 사실과 원래 시각을 밝히며 새 평가라고 부르지 않는다.

내용 수정은 구체적인 근거에 따라 한다. 90점 도달, 전축 5점, 점수 하락 금지를 종료 기준으로 삼지 않는다. 사실 대조는 제공 원문과의 일치·불일치이며 외부 진실성을 보증하지 않는다. 핵심 사실 충돌은 attention_flags와 PROVISIONAL_FACT_CONFLICT로 점수 해석을 제한한다. 규격 위반도 별도 표시하고 작성 점수와 합산하지 않는다. 기술적으로 가능한 면접 해결책을 실제 과거 행동으로 승격하지 않는다.

## 집계 이후

호스트는 [저장 계약](workflow-storage.md)에 따라 실제 호출 기록을 남기고 `record_review.py`로 점수 원장에 기록한다. 전체 수정 요청이면 근거에 따라 새 버전 수정·회귀 검토·필요한 재평가·경험 되먹임을 수행한다. [5단 리포트](diagnostic-report.md)에 기계 집계와 정성 판단, 면접 확인 질문, 다음 행동과 기록 위치를 함께 제공한다. 집계 Markdown만 출력하고 전체 파이프라인을 완료했다고 보고하지 않는다.

## 버전과 결과 해석

v5는 세션 토큰 schema_version=3, evaluation_version=5.0을 사용하고 집계 JSON은 schema_version=2다. 과거 평가를 이 형식으로 재표시하거나 G/J만 빼서 새 평가라고 부르지 않는다. 기존 원장에 평가 버전과 원 실행을 보존한다.

state는 작성 평가 상태이며 원고의 제출 준비 완료를 뜻하지 않는다. questions의 compliance와 fact_review, attention_flags를 함께 보고한다. 사소한 사실 차이는 해당 주장의 정정으로 다루고 핵심 역할·성과 충돌과 구별한다. 같은 문제를 여러 축에서 다룰 때는 각 축에서 빠진 설명의 차이를 근거로 남긴다.
