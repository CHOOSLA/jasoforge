# 선행 조사와 동적 context 계약

전체 작성·평가에서는 대상과 자료 범위를 먼저 확정한다. 문장만 수정하는 작업에는 전체 조사를 추가하지 않는다. 기존 자료가 충분하면 재사용하고, 새 검색은 공고·회사·사업부·직무의 부족하거나 시점이 달라진 정보를 보충한다.

## 확인할 항목

| 영역 | 확인할 것 | 연결되는 단계 |
| --- | --- | --- |
| 지원 식별 | 시즌, 채용 법인, 부서, 직무, 인턴/신입 등 전형, 공고 URL, 마감 | 버전·지원서키·원장·최종 브리핑 |
| 지원 조건·일정 | 근무지, 고용 형태, 전형별 일정, 복수지원 제한, 어학 성적 유효기간, 제출 서류·방법 | 지원 가능 여부·지원 전 점검·일정표 |
| 조직 관계 | 실제 고용 법인과 고객사/자회사/서비스의 관계 | 대상 확인·직무 분석·면접 질문 |
| 회사 | BM·제품·고객·공식 가치·투자/사업 방향·관련 산업 이슈 | 직무 선택·지원동기 |
| 사업부/제품 | 담당 제품, 고객, 운영/신규개발/R&D 등 환경, 공개된 현안 | 경험 매칭·업무 연결 |
| 직무 | 담당업무 원문 순서, 필수/우대, 스택, 업무 제약·확인 가능한 기술 쟁점 | 작성·HR/TECH 평가 |
| 문항 | 실제 질문·작성 방법·규격·블라인드 규정 | spec·린트·작성 8개 축 적용 범위 |
| 경험 | 사용자 설명·메모·경험 기록에서 얻은 개인 역할·판단·행동·결과와 출처 | 작성·선택적 근거 대조·되먹임 |

과거 지원서를 평가할 때는 당시 공고를 찾는다. 현재 공고로 대체했다면 같은 조건의 평가라고 말하지 않는다. 공고에 공개되지 않은 내부 시스템·채용자 속마음을 검색 결과 없이 채우지 않는다.

## context.json

고정 기업명이나 특정 업종의 만점/탈락 처방 대신 다음 정보를 전달한다. 아래는 에이전트가 채우는 계약이며 사용자가 직접 파일을 작성할 필요는 없다.

- `application_key`, `recruitment_season`, `recruitment_track_type`: 지원 식별.
- `company`, `department`, `job_role`: 확인된 대상. 부서 미공개는 null과 unresolved 항목으로 기록.
- `application_url`, `deadline`: 확인한 출처와 날짜. 지원일과 마감일을 구별.
- `work_location`, `employment_type`: 근무지·고용 형태의 원문과 source_id. 인턴 전형과 정규직 전환 확정을 혼동하지 않는다.
- `recruitment_schedule`: 단계·일시/기간·시간대·source_id·확인 상태의 배열. 발표 예정일·응시일·제출 마감을 구별한다.
- `application_checks`: 지원 전 조건별 원문·source_id·`status`(confirmed / unresolved / not_applicable)·사용자 충족 여부·필요한 행동. 복수지원 제한, 어학 유효기간/기준일, 필수 서류, 지원 자격, 제출 방법을 확인한다. 공고에 없는 조건은 지어내지 않으며 ‘기재 없음’과 ‘제한 없음’을 구별한다.
- `organization_contract`: `declared_target`, `parent_legal_entity`, `client_service_domain`, `relationship_evidence`.
- `key_responsibilities`: 공고의 순서를 보존한 업무 목록. 각 항목에 원문·source_id·공식 우선순위 또는 중요도 해석의 근거를 둔다.
- `required_qualifications`, `preferred_qualifications`, `required_hard_skills`: 필수/우대를 구분. 스택이 언급됐다는 이유만으로 필수로 바꾸지 않는다.
- `layer1_company`, `layer2_department`, `layer3_job_edge_cases`: 각 층의 확인 사실·출처·조사 시점·미확인. 기술 쟁점은 `confirmed_requirement`와 `analysis_hypothesis`를 구별한다.
- `sources`: source_id별 URL/로컬 경로/Notion 페이지, 확인일, 관련 원문. 요약만으로 중요한 평가 근거를 대체하지 않는다.
- `fact_check`: 선택적으로 제공된 경험 원문·종류·주장 연결표. [근거 대조 계약](fact-checking.md)에 따라 호스트가 생성한다. 자료가 없는 첫 사용은 필드를 생략할 수 있다. 코드와 당시 동기를 혼동하지 않는다.
- `unresolved`: 부족한 자료, 평가에 주는 영향, 확인 방법.

전체 작업에서는 이 항목을 확인하되 모르는 항목을 가짜 값으로 채우지 않는다. 제한된 평가라면 누락된 회사·직무 조건을 표시하고 회사 적합성 결론을 제한한다. CLI는 임의 context 객체도 받을 수 있으므로 **전 항목을 검증한 것은 에이전트가 직접 확인·보고할 책임**이다. JSON 생성만으로 조사 완료를 선언하지 않는다.

context에는 칭찬·목표점수·면책·합불·평가자에게 줄 결론을 넣지 않는다. 동일한 조사와 문항을 작성 단계와 평가 단계에 전달하지만 작성 대화·수정 변론은 평가 패킷에서 제외한다.

## 전형별 평가와 지원 전 점검

`recruitment_track_type`은 가능한 경우 `CONVERTIBLE_INTERN`, `INTERN`, `NEW_GRAD`, `EXPERIENCED`로 기록하고 실제 공고 표현과 출처를 함께 보존한다. 혼합/미공개 전형을 임의로 하나로 고르지 않는다. run_pipeline.py는 이 값에 맞는 지침을 HR/TECH 패킷에 주입한다. 인턴·신입에는 공고에 없는 경력직 실적을 요구하지 않고, 경력도 실제 공고의 경력 수준과 책임을 기준으로 평가한다.

research.md와 연동 모드의 지원 현황 본문에는 **지원 개요, 전형 일정표, 지원 전 조건표**를 남긴다. 마감만 기록하고 나머지 지원 조건을 확인한 것으로 처리하지 않는다. 미확인 조건·일정은 최종 리포트의 다음 행동에 연결한다. 내부 점수와 지원 자격/제출 요건 충족 여부는 별도로 보고한다.

## 직무 선택과 경쟁 현황

직무가 미정이면 사용자 설명·경험 노트·제공 자료를 공고의 업무/자격/우대와 대조해 경험 접점과 부족한 준비를 설명한다. 경험이 아직 파악되지 않았으면 [경험 수집](experience-intake.md)으로 필요한 맥락부터 얻는다. 지원 대상 없이 경험 정리만 요청한 경우 여기의 회사 조사를 수행하지 않는다. 지원 방향 탐색도 요청했다면 관심·경험에서 잠정 후보를 잡고, 실제 공고를 확인한 뒤 1순위와 대안의 이유를 설명한다. 경험의 기술명 수를 적합도 점수로 환산하지 않는다.

플랫폼이 관심자·작성자·지원 완료자 수를 구분하면 그대로 표시하고 조회시각을 남긴다. 실제 모집 인원·지원자 집계 정의가 없으면 경쟁률을 계산하지 않는다. 낮게 보이는 숫자만으로 지원 자격이나 직접적인 업무 접점을 뒤집지 않는다.

## 저장과 전달

로컬 research.md 또는 Notion 조사 페이지에 사람이 읽을 조사 내용과 출처를 남기고 context.json으로 필요한 내용을 전달한다. 기존 연구가 있으면 먼저 읽어 중복을 피한다. 공식 정보의 변경과 평가자의 해석 변경을 별도로 기록한다. 대상·문항·context가 바뀌면 기존 패킷을 고치지 말고 새 평가 실행을 만든다.
